# Embeddings & Hybrid Search

This project's discovery layer combines:

1. **Text matching** — ILIKE on title/description + tokenized expansion.
2. **Category expansion** — find related categories via cosine distance on category embeddings.
3. **Product semantic rank** — re-rank candidates by cosine distance on `products.embedding`.

Embeddings are 384-dim, generated by sentence-transformers `all-MiniLM-L6-v2` via `server/app/core/embeddings.py`. Storage is `pgvector` with HNSW indexes.

## When this skill applies

- Tuning the `/products/search`, `/products/facets`, `/search/suggest` endpoints.
- Adding a new searchable entity (e.g., stores) that needs embeddings.
- Backfilling missing embeddings (see `server/scripts/backfill_category_embeddings.py`).
- Debugging "the search results aren't relevant".

For DB / index DDL see `postgres-schema`. For the React-side search UX (autocomplete, debouncing), see `product-discovery-ui`.

## Embedding generation (must be deterministic)

```python
# server/app/core/embeddings.py
from sentence_transformers import SentenceTransformer
import threading

_model_lock = threading.Lock()
_model: SentenceTransformer | None = None
DIM = 384

def get_model() -> SentenceTransformer:
    global _model
    with _model_lock:
        if _model is None:
            _model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
    return _model

def embed_text(text: str) -> list[float]:
    vec = get_model().encode(text or "", normalize_embeddings=True)
    return vec.tolist()
```

- `normalize_embeddings=True` so cosine ≈ dot product and HNSW is well-behaved.
- Lazy-load + lock — the first request loads the model (~80MB); never load at import time, it breaks Alembic.
- Same model in dev, prod, scripts. Switching model = rebuild ALL embeddings.

## What text to embed

For a product, concatenate the most signal-rich fields with separators:

```
title. category_name. brand. key attributes (color, material). description (truncated to 200 words).
```

Order matters — earlier tokens get higher weight. Don't dump everything; embeddings degrade on noisy long inputs.

For categories, just `name. parent.name. synonyms` is enough.

## When to (re-)compute

| Trigger | Action |
| --- | --- |
| Product create / title or description change | Recompute on save (services.py) |
| Category rename | Recompute the category embedding |
| Model upgrade | Backfill all rows via script |
| Bulk import | Batch in groups of 32 — `model.encode(list_of_strings)` is way faster than one-by-one |

```python
def save_product(db, body):
    p = Product(**body.model_dump())
    p.embedding = embed_text(_embed_text_for(p))
    db.add(p); db.commit(); return p

def _embed_text_for(p: Product) -> str:
    parts = [p.title, p.category.name if p.category else "", p.brand or ""]
    parts += [f"{k}: {v}" for k, v in (p.attributes or {}).items()][:6]
    parts.append((p.description or "")[:1000])
    return ". ".join(filter(None, parts))
```

## Index DDL (in a migration)

```sql
CREATE EXTENSION IF NOT EXISTS vector;

ALTER TABLE products
  ADD COLUMN IF NOT EXISTS embedding vector(384);

CREATE INDEX IF NOT EXISTS ix_products_embedding_hnsw
  ON products USING hnsw (embedding vector_cosine_ops);

-- Same for categories
ALTER TABLE categories
  ADD COLUMN IF NOT EXISTS embedding vector(384);
CREATE INDEX IF NOT EXISTS ix_categories_embedding_hnsw
  ON categories USING hnsw (embedding vector_cosine_ops);
```

HNSW supports cosine, L2, and inner-product ops; pick `vector_cosine_ops` so `<=>` returns cosine distance (lower = closer).

## Hybrid search query (the pattern used in `product/services.py`)

```python
def search_products(db, q: str, *, limit: int = 24):
    q = q.strip()
    if not q:
        return []
    q_vec = embed_text(q)

    # 1) cheap text candidate pool
    text_filter = or_(
        Product.title.ilike(f"%{q}%"),
        Product.description.ilike(f"%{q}%"),
    )

    # 2) category expansion — pull categories close to the query
    close_categories = db.execute(
        select(Category.id)
        .order_by(Category.embedding.cosine_distance(q_vec))
        .limit(5)
    ).scalars().all()
    if close_categories:
        text_filter = or_(text_filter, Product.category_id.in_(close_categories))

    # 3) candidates, then semantic re-rank
    candidates = (
        select(Product)
        .where(text_filter)
        .where(Product.is_active.is_(True))
        .order_by(Product.embedding.cosine_distance(q_vec))
        .limit(limit * 3)
    )
    rows = db.execute(candidates).scalars().all()

    # 4) final blend: score = α * (1 - cosine) + β * popularity_signal
    return _rerank(rows, q_vec, limit)
```

- Pull `limit * 3` candidates and re-rank — pure vector search misses brand/exact-title matches.
- Combine with a popularity signal (`sold_count`, `rating`) so the freshest semantic match doesn't trump a clear best-seller.
- ILIKE handles exact substring (typed brand names). Vector handles "thingy that holds my keys" → keychain.

## Tuning HNSW

- `m` (default 16) — higher = better recall, more memory. 16 is fine until > 1M rows.
- `ef_construction` (default 64) — index build quality.
- `ef_search` at query time: `SET LOCAL hnsw.ef_search = 100;` — increase for better recall on hard queries.

For most catalogs under 500k products, defaults are fine. Don't tune blindly — measure recall@k on a labeled query set first.

## Autocomplete

Two-pass:

1. Cheap prefix match in Postgres: `WHERE lower(title) LIKE lower(:q) || '%' LIMIT 6`.
2. If fewer than 3 results, fall back to a semantic top-5.

Return `{ terms, categories, products }` so the frontend can render grouped suggestions. Debounce 200ms client-side (`product-discovery-ui`).

## Backfill scripts

Existing: `server/scripts/backfill_category_embeddings.py`. Pattern for products:

```python
def backfill():
    db = SessionLocal()
    BATCH = 64
    q = select(Product).where(Product.embedding.is_(None))
    cursor = db.execute(q).scalars()
    batch = []
    for p in cursor:
        batch.append(p)
        if len(batch) == BATCH:
            _embed_batch(db, batch); batch.clear()
    if batch: _embed_batch(db, batch)

def _embed_batch(db, batch):
    texts = [_embed_text_for(p) for p in batch]
    vecs = get_model().encode(texts, normalize_embeddings=True, batch_size=BATCH)
    for p, v in zip(batch, vecs):
        p.embedding = v.tolist()
    db.commit()
```

Always batch. One-at-a-time is 30–50× slower.

## Caching the model in tests

`server/conftest.py` runs on SQLite — `pgvector` types won't exist. Either:

- Skip embedding columns under SQLite (dialect dispatch on the column type), OR
- Stub `embed_text` to return `[0.0] * 384` in a test fixture.

Don't load the real model in the test process unless you're running an integration test against real Postgres.

## Common mistakes to flag

- Loading the model at module import time → Alembic / fast startup paths now wait 2 seconds.
- Computing embeddings one at a time in a loop → 30× slower than batching.
- Different embedding text composition at write time vs query time → query embedding lives in a different region of vector space.
- Forgetting to normalize embeddings → cosine distance is undefined, HNSW ranking degrades.
- Pure vector search with no ILIKE fallback → "iPhone 15 Pro Max" matches nothing if no product has that exact phrase indexed cleanly.
- Mixing two embedding models (e.g., MiniLM for products, ada-002 for queries). The dim mismatch alone breaks search; semantically they're incomparable anyway.
- HNSW index added in `__table_args__` instead of a migration — breaks SQLite tests.

## Checklist

- All searchable entities embed with the same model + normalization.
- Query embedding uses the same text-composition recipe as the write path.
- Hybrid: ILIKE candidates → category expansion → vector re-rank → popularity blend.
- HNSW index on every embedding column, defined in a migration.
- Backfill script exists and batches.
- Tests don't require the real model (stub or skip vector cols on SQLite).
